# AI SQL Query Optimizer

Learns to pick between a full table scan and an index scan for SQLite queries, and benchmarks that choice against a classic rule-based heuristic.

```
SQL -> parser -> selectivity estimate -> feature extraction -> Random Forest -> FULL_SCAN | INDEX_SCAN -> SQLite -> results + timing
```

## Run it

```bash
pip install -r requirements.txt
python benchmark.py 300      # times both plans on 1,200 random queries (10k to 200k rows)
python train.py              # trains the Random Forest, writes benchmarks/results.md
python cli.py "SELECT * FROM students WHERE cgpa > 8.5 AND department = 'CSE'"
streamlit run app.py
pytest
```

## How it works

- `optimizer/parser.py`: regex parser for `SELECT ... FROM ... WHERE a op v [AND ...] [ORDER BY] [LIMIT]`.
- `optimizer/stats.py`: column statistics (percentiles, value counts) give a selectivity estimate without running the query.
- `optimizer/plans.py`: forces a plan in SQLite with `NOT INDEXED` or `INDEXED BY`, and times each (median of 3 runs).
- `optimizer/features.py`: log table size, combined selectivity, best indexed selectivity, condition counts, equality flag.
- `benchmark.py` labels every query with whichever plan was actually faster; `train.py` fits a Random Forest on 80% and evaluates on 20%.

## Results

See `benchmarks/results.md` (regenerated by `train.py`). Timings depend on your machine.

## Limits

AND conditions only (no OR), single table, no JOINs yet. Queries with no usable index always use a full scan. Plan differences on SQLite are small in absolute terms, so this project is about the method and the evaluation more than big speedups. Natural next steps: OR support, JOIN plans (nested loop vs hash vs index), a larger and more skewed dataset.
